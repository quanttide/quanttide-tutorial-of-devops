# 发布

发布不是“打一个标签”这么简单，而是把一个版本交付到所有应该到达的地方。

一个版本可能需要同时完成：

- Git tag
- CHANGELOG
- GitHub Release
- crates.io / PyPI / npm / pub.dev
- 容器镜像仓库
- Linux / Windows / macOS 二进制资产
- 内部制品库或客户交付包

所以发布教程按这条链路组织：

```text
确认发布对象
→ 确认发布目标
→ 发布前审计
→ 选择 CLI 发布或手动操作
→ 执行发布
→ 发布后审计
→ 处理异常并记录结果
```

## 核心理念：小步快跑

发布不求大、不求全，有改动就尽早发。每个版本只包含少数几个变更，可以降低单次发布风险，也能让团队更快拿到反馈。

小步快跑不是降低质量，而是把大版本拆成多个小版本，每个小版本都走完完整的发布流程。一个功能可以分两次发：先发后端接口（`v0.2.0`），再发前端页面（`v0.2.1`）。修复 bug 不必攒到下次大版本，修完就发（`v0.2.2`）。

预发布版本（alpha、beta、rc）也是小步快跑的具体实践。每个阶段都发一个版本标记，不等所有工作完成才打标签。

## 本章怎么读

第一次发布时按顺序读：

1. [语义化版本](version.md)：先确定版本号和 tag 写法。
2. [发布执行](publish.md)：选择 CLI 发布或手动操作。
3. [发布审计](audit.md)：发布前后按清单检查。
4. [异常情况](exception.md)：发布失败、缺 Release、缺制品或 tag 错误时再看。

## 管理员与 AI 的配合

管理员先确认“该发什么”：发布哪个仓库、哪个 scope、哪个版本、要发布到哪些目标、是否允许手动操作。

AI 再确认“能不能发”：检查配置文件、CHANGELOG、Git tag、CI workflow、制品库配置、发布日志和安全风险。

如果管理员想发布，但事实源缺失，先补事实源；如果命令执行成功，但 registry、Release 或二进制资产缺失，不能说这个版本已经发布完成。

## 最小发布闭环

发布前至少确认：

- 目标版本与配置文件一致。
- CHANGELOG 有对应版本条目。
- 工作区干净。
- 构建和测试已通过。
- 发布目标已列全。
- 凭证在组织、仓库或受控环境中配置，没有写进仓库。

发布后至少确认：

- tag 已推送并指向正确提交。
- GitHub Release 存在，正文来自 CHANGELOG。
- 对应制品库版本可查询。
- 二进制资产、容器镜像或内部制品能访问。
- CI/CD release job 成功。
