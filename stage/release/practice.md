# 只要版本发的够快，Bug 就追不上我

这是公司工作教程 DevOps 章 release 节的主要内容。

## 自动化发布环境下出错率高是常态

和手动发布版本不同的是，在 AI 结合 CICD 发版本的情况下，版本过程中出错是太正常不过的事情了。AI 和 CICD 都是高异常大户。

我们恰恰就是希望各种自动化门禁发现各种问题，包括但是不限于编译异常、测试覆盖率不够、发布配置异常等等。

因此，不需要担心版本发的不整齐，如果出了问题就不停地用新版本覆盖，版本序列不整齐就升级版本号。

比如说，这会儿公司的 CTO 助理正在发布数据云命令行工具的 v0.1，即使发布到 v0.1.9 还在修 CI。这就是把 patch 当成 rc 预发布了。没关系，完成以后发 0.2.0 就覆盖了 0.1.x 的过往。

## 在预发布版本充分试错

和手动发布版本不同的是，为了人类减少被混乱的正式版困扰，预发布版本在自动化发布中显得格外重要。

一般的社区习惯是 alpha、beta、rc。其中 rc 就是用来测试 CICD 等非功能部分是否正常。alpha 和 beta 在实际使用时容易模糊，以团队关于 alpha 和 beta 的约定为准。

最佳实践是，保持正式版本的 API 大体正常即可。少数正式版异常可以通过增加 patch 覆盖，小问题可以跳过预发布版本快速发布。

一般来说，在发布新的 major 和 minor 版本时要尽可能严格地走一遍 alpha、beta、rc，特别是有 break change 时要格外小心。

不用怕犯错。现代 CICD 系统和工程规范都留足了容错空间。在生产环境下充分犯错，才能够建立对版本发布的正确手感。
