# 单测覆盖率卡住了？那是架构在给你发信号

AI 帮你写单测已经不是什么新鲜事了。你告诉它"给这个函数写个测试"，它噼里啪啦输出一堆，看起来都挺像那么回事。但问题是——你真的敢信吗？

我们的经验是：**AI 生成的单元测试可以放一放，集成测试以上必须自己跑。** 不是不信任 AI，是它不真正理解你的业务意图。它读你的代码，模仿结构，生成看起来很像的测试用例——但它不知道这个函数"应该"返回什么才是对的。单测数量多起来你审不过来，可以接受一些良莠不齐。但集成测试验证的是你的业务流程有没有跑偏，这块不能让 AI 替你做判断。

那单测写到什么程度算够？我们定的是 **80%**。不是拍脑袋定的——是留了 20% 给 IO、网络、数据库连接这些不好单测的部分。Python 可以 mock，Rust 就直接上集成测试。各自用各自顺手的方式。

但 80% 这个数字本身不是重点。重点是你发现自己卡在六七十上不去的时候，别一个劲儿补测试用例。

覆盖率上不去，大概率不是测试写得不够多。是**架构在给你发信号**。

最常见的问题是什么？纯逻辑和 IO 耦合。一个函数里既有计算逻辑，又有几十行 `print`，又有文件写入。这种写法不是"不够优雅"——是根本没办法单测。

解法很简单：**组装和写入分离。** 把计算逻辑抽成一个纯函数，可单测。IO 操作单独一两行，集成测试覆盖。拆完之后，那个让你头疼的覆盖率数字自己就上去了。

```python
# 之前：逻辑和 IO 揉在一起，单测无从下手
def process_and_save(data):
    result = heavy_computation(data)
    print("Step 1 done")
    print("Step 2 done")
    with open("output.csv", "w") as f:
        f.write(result)

# 之后：拆成两步
def assemble(data):        # 纯逻辑，好单测
    return heavy_computation(data)

def write(result, path):   # IO 操作，集成测试覆盖
    with open(path, "w") as f:
        f.write(result)
```

还有一个很多人搞混的问题：单测和集成测试到底什么区别？不是"集成测试更厉害"或者"更全面"。它们回答的问题根本不一样。

**单元测试问的是：这个函数对输入给出了正确的输出吗？**
**集成测试问的是：这一串操作能正常串起来吗？**

所以你感觉"单测不靠谱"的时候，很多时候不是单测没写好——是该升级到集成测试了。单测验证了每个零件能用，集成测试验证了零件拼起来能跑通业务。两个都做了，才算测到位。

最后说一下重构的顺序。不管改动大小，我们的习惯是：

先写清楚你想怎么改，在 dev-guide 里把设计意图说清楚。然后对齐 ROADMAP——确认这个改动在当前版本计划里，不在就加进去。接下来**先改测试**，把期望的新行为写成测试用例，再改代码实现到测试通过。最后跑集成测试，验证端到端流程没断裂。

先测试后代码不是教条。是让你在动手之前就把"做完的标准"定义清楚。不然写完代码再补测试，很容易变成"对着实现写验证"，丢了测试的本意。
